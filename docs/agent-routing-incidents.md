# AgriGraph 真实对话事故复盘与面试谈资

这份文档记录统一 AgriGraph 上线后，通过真实模型和真实多轮对话发现的问题。重点不是“Prompt 写错了”，而是说明概率模型、确定性业务规则、会话状态和用户界面如何互相影响，以及如何把偶发错误变成可复现、可测试的工程问题。

## 1. 最有代表性的事故

真实对话：

```text
用户：我想在扬州种水稻，我该干什么
助手：给出通用步骤，并询问目前处于哪个阶段
用户：我还没有开始种植
助手：为了继续处理，请补充具体症状
```

这不是 Clarify 节点本身写错了。可能的实际执行链是：

```text
LLM路由误判 capabilities=[diagnosis]
  -> 程序校验 diagnosis 必须有 crop + symptom
  -> crop 已有，symptom 缺失
  -> 确定性地进入 clarify
  -> 询问“具体症状”
```

后半段程序完全按规则执行，真正的问题是：一次概率路由误判被确定性校验放大成了非常突兀的用户体验。

## 2. 根因不是一个，而是四层叠加

### 2.1 状态模型缺少业务维度

旧状态只有：

```text
crop / city / region / symptom / need
```

但“我还没有开始种植”描述的是种植阶段，不属于任何已有槽位。模型只能把它勉强映射到最接近的能力。

修复后增加：

```text
growth_stage = 未开始种植
has_symptom = false
active_goal = 种植准备
pending_slot = growth_stage
```

### 2.2 助手提出了系统没有记录的问题

旧版助手会自然地问“目前处于哪个阶段”，但图状态没有记录自己正在等待 `growth_stage`。下一轮“还没有开始种植”因此被当成新请求重新分类。

新版 Direct 节点会识别自己回答末尾提出的关键问题，并写入 `pending_slot`。下一轮优先填槽，再决定是否需要重新路由。

### 2.3 概率语义与确定性规则没有分层

LLM适合判断模糊意图，但不适合独自维护“未种植且无症状时不能进入病虫害诊断”这种业务不变量。

新版增加程序约束：

```text
growth_stage == 未开始种植
and has_symptom == false
=> 删除 diagnosis capability
=> 不允许因为缺 symptom 进入 clarify
```

LLM即使仍然偶发误判，最终执行路线也不会违反业务事实。

### 2.4 内存记忆与浏览器历史可能错位

`MemorySaver`只存在于后端进程内。后端重启后，浏览器仍显示旧聊天记录，但图状态已经清空，用户看到的上下文和模型实际看到的上下文会不一致。

新版在 checkpointer 为空时，将前端保存的历史反序列化为 LangChain 消息并恢复；已有图状态时则忽略前端历史，避免重复注入。

## 3. 同一轮改造发现的其他问题

| 问题 | 表现 | 根因 | 修复 |
|---|---|---|---|
| 结构化路由返回空值 | `NoneType has no attribute capabilities` | OpenAI兼容模型偶尔没有调用结构化工具 | 空值和非法结构统一进入保守回退 |
| 路由器只看最后一句 | “为什么没有建议”被当成新问题 | 为兼容工具调用而丢掉最近对话 | 压缩最近六条对话，再包装成明确分类任务 |
| 追问只解释不补建议 | 能承接上文，但又让用户选择想了解哪部分 | Prompt只要求核对上文，缺少结果交付约束 | 解释后必须按当前目标和阶段补充3到5条行动项 |
| 路由器直接续写用户问题 | 返回农业答案而不是 `RouteDecision` | 最后一条原始消息诱导模型回答 | 最后一条改为“请分析以下对话并调用RouteDecision” |
| Direct输出伪工具调用 | 页面出现 `get_weather_forecast {...}` | Direct没绑定工具，却复用了工具版系统提示 | Direct和ReAct使用独立系统提示 |
| 单能力误进Planning | 只问天气却生成综合行动计划 | 只做了ReAct向Planning升级，没有反向校正 | 单能力且未明确要求计划时降回ReAct |
| Planning默认天气+政策 | 用户没问政策却出现政策章节 | 空capabilities被程序强行填默认值 | 按实际字段和能力选择模块，不再猜默认需求 |
| 省份被当成城市 | 用“江苏”查询城市天气 | LLM字段抽取缺少粒度校验 | 省级名称不能写入city，缺城市时明确追问 |
| 空政策章节 | 输出“本模块无相关建议” | 汇总Prompt强制固定两个章节 | 只展示真实成功模块，禁止空章节占位 |
| 过期日期进入未来计划 | 把昨天写成接下来要做 | 天气Prompt没有当前日期边界 | 注入当天日期并忽略早于当天的预报 |
| 否定事实被忽略 | “没有症状”仍进入诊断 | 只存症状文本，不存真假状态 | 增加 `has_symptom` 并解析否定表达 |

## 4. 为什么不是把 temperature 调成 0

温度降低只能减少采样波动，不能解决：

- 第三方兼容接口不严格执行 `tool_choice`；
- 模型对长对话中哪些词更重要理解不同；
- 状态Schema根本没有 `growth_stage`；
- 后端重启导致历史丢失；
- 业务不变量没有写进程序。

即使 `temperature=0`，线上模型服务也不承诺逐Token完全确定。可靠性必须来自状态建模、校验、回退和回归测试，而不是把一次模型输出当成事实。

## 5. 最终设计

```text
用户输入
  -> 若存在 pending_slot，优先解析为上一问题的答案
  -> 结构化LLM路由：route + capabilities + slots + confidence
  -> 程序补充阶段/否定表达解析
  -> 程序执行业务不变量和字段粒度校验
  -> direct / react / planning / clarify
  -> Direct若提出关键问题，将其写回 pending_slot
  -> MemorySaver持久当前进程状态，前端历史负责重启恢复
```

职责边界：

- LLM负责模糊语义、指代和开放式表达。
- Pydantic负责输出形状。
- 程序规则负责业务事实和状态转移。
- LangGraph负责节点、条件边和检查点。
- 测试负责把偶发对话固化成确定性回归用例。

## 6. 验证证据

新增真实事故回归测试：

- 助手询问阶段后写入 `pending_slot=growth_stage`。
- “我还没有开始种植”填充阶段并清除 pending slot。
- 路由器即使故意返回 diagnosis，也会被业务不变量纠正。
- “还没有症状”保存 `has_symptom=false`，不会追问症状。
- 后端空状态可以从前端历史恢复最近对话。
- “为什么没有建议”不仅承接历史，还必须补充3到5条当前阶段可执行行动。

旧实现尚未删除时完整后端回归曾为 `71 passed`；删除重复 Agent 与对应测试后，当前主线回归集为 `53 passed`。真实智谱模型复测也确认状态依次变为：

```text
种植咨询，等待 growth_stage
  -> growth_stage=未开始种植
  -> has_symptom=false
  -> active_goal=种植准备
  -> route=direct
```

## 7. 面试 STAR 讲法

### Situation

统一 LangGraph 主流程上线后，真实用户回答“还没有开始种植”，系统却追问“具体症状”。同一句话重跑时有时正常、有时错误，说明不是普通的固定代码分支Bug。

### Task

目标不是针对这一句话增加一个 `if`，而是找出概率路由为什么会被放大，并让同类阶段回答、否定表达和服务重启都能稳定处理。

### Action

1. 记录每轮 `route/capabilities/missing_fields/context`，还原错误路径。
2. 发现状态缺少种植阶段，且助手提出的问题没有写入机器状态。
3. 新增 `growth_stage/has_symptom/active_goal/pending_slot`。
4. 将“未种植且无症状不能诊断”等规则放进程序，不交给LLM自由决定。
5. 增加前端历史反序列化，解决MemorySaver重启失忆。
6. 用故意误判的假路由器写回归测试，再用真实模型复测。

### Result

原始四轮对话稳定走 `direct`，用户不再被要求提供不存在的症状；状态能正确显示“未开始种植、无症状、种植准备”。继续追问“为什么没有建议”时，真实模型会直接补充5条种植准备行动，不再只解释后反问用户。单一主线收敛后的完整后端测试为53项全部通过。

## 8. 高频追问与回答

### 为什么不用纯LLM管理状态？

自然语言理解可以交给LLM，但“当前等待哪个字段”“否定事实是否成立”“哪些能力在当前阶段绝对不允许”属于业务状态和不变量。纯LLM可以演示，无法提供可测试的稳定性。

### 为什么不把所有意图都写成规则？

农业表达方式很多，全部规则化会快速膨胀，也处理不好指代和改写。因此采用“LLM负责开放语义，程序负责边界”的混合方案。

### 为什么有missing_fields还需要pending_slot？

`missing_fields`表示执行某个能力前缺少的参数；`pending_slot`表示助手上一轮明确问了什么。Direct回答也可能提出问题，但它不一定对应工具必填字段，两者语义不同。

### MemorySaver有什么生产风险？

它随进程消失，也无法多实例共享。当前通过前端历史恢复解决本地演示连续性；生产环境应替换为Postgres/Redis类持久化checkpointer，并让服务端成为唯一可信状态源。

### 这次最重要的工程收获是什么？

模型错误不可怕，可怕的是没有把错误限制在边界内。好的Agent架构不是追求LLM永不误判，而是让一次误判不会违反业务事实，并且能被日志复现、被测试固定、被程序纠正。
