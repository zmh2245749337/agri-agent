# AgriAgent 技术决策记录

这份文档记录项目当前版本最重要的工程取舍。它回答的不是“用了哪些技术”，而是“为什么在这个数据规模和用户场景下这样做”。

## 目标与边界

AgriAgent 的目标是验证一个端到端农业 Agent 系统：能理解自然语言或图片输入，按需查询病虫害知识、天气和补贴政策，并把多个结果整合成可执行建议。

当前版本不是生产级农技诊断平台。知识库规模有限，政策存在时效性，图片诊断也缺少田间环境和生育期等完整信息。因此系统会区分本地核实结果、联网检索结果和模型通用知识推测，并在低可信度路径上明确提示用户复核。

## 决策总览

| 问题 | 当前选择 | 没有直接采用的方案 | 主要依据 |
|---|---|---|---|
| 请求路由 | Pydantic结构化输出 + 程序字段校验 | 关键词单规则或让模型直接执行 | 同时得到route、capabilities、slots和confidence，低置信可追问 |
| Agent编排 | AgriGraph混合Direct/ReAct/Planning/Clarify | 两套平级入口或所有请求动态规划 | 在一张图中混合确定性与动态行为，表单只是强制planning模式 |
| 政策匹配 | BM25 + 地区过滤 + BGE 精排 | 只用关键词或直接上向量库 | 同时兼顾召回、语义与地区约束；28 条数据无需向量数据库 |
| 病虫害匹配 | RapidFuzz 主查 + 长上下文对照 | GraphRAG | 77 条数据规模小，图构建成本与收益不匹配 |
| Agent 间协作 | 进程内 A2A-lite | 完整 A2A JSON-RPC/HTTP | 当前只有 3 个同进程子 Agent，先落能力名片与任务状态机 |
| 图片处理 | 视觉模型转文字，再进入文本 Agent | 视觉模型直接负责诊断和工具调用 | 免费视觉模型不支持 Function Calling，拆分后职责更清晰 |
| LangGraph | 只保留统一 AgriGraph 主流程 | 在运行代码中维护多版 Agent | State与条件边统一槽位、追问、工具循环和 Planning；历史方案只留在笔记 |

## 1. 为什么收拢为统一 AgriGraph

早期版本把 `PlanningAgent` 结构化表单和 `ChatAgent` 自由对话作为两条平级入口。两种编排方式本身合理，但会让业务状态、来源说明和用户体验形成两套主线。当前产品前端只保留聊天入口，所有自然语言请求都进入 `AgriGraph`；`/planning` 仅作为内部调用和接口测试能力保留，不再形成第二个用户入口。

路由模型使用 Pydantic 结构化输出产生 `route + capabilities + slots + confidence`。程序再按能力校验必填字段：普通问题进入 Direct，单项查询进入 ReAct，多项需求或明确计划进入 Planning，字段不足进入 Clarify。槽位保存在 LangGraph State 中，下一轮只需补充缺失信息。

路由输入不是只看最后一句，也不是把原始聊天消息直接交给模型续写，而是把最近六条用户/助手对话压缩后包进一条明确的“分类任务”。这样既兼容部分 OpenAI 兼容模型对结构化工具调用的要求，也能理解“为什么没有建议”“最近必须做什么”等指代上文的追问。程序还会校验省级地区不能冒充天气城市，并把只有一个能力、又没有明确要求计划的请求降回 ReAct。

Direct 与 ReAct 使用不同系统提示：Direct 明确禁止输出伪工具名或编造实时查询，优先承接上下文并检查农时结论的一致性；ReAct 才绑定真实工具。Planning 汇总只渲染实际成功的模块，不再为了固定模板输出空政策章节。

真实对话中还发现，“助手问了种植阶段”不等于状态机知道自己问了什么。当前状态因此增加 `growth_stage + has_symptom + active_goal + pending_slot`：短回答优先填充待回答槽位，否定事实触发程序不变量，Direct提出的新问题也会写回状态。内存checkpointer为空时可从前端历史恢复消息。完整错误链、验证用例和面试STAR讲法见 [AgriGraph真实对话事故复盘](agent-routing-incidents.md)。

`PlanningAgent` 仍保留并发与失败隔离，但作为 Planning 节点执行，并接受 `capabilities` 只调用本轮需要的专业模块。这样既没有丢掉确定性工作流，也不再把它暴露为另一套产品架构。

## 2. 为什么 Function Calling 暴露原始工具

AgriGraph 的 ReAct 节点暴露的是返回结构化数据的底层工具，而不是各子 Agent 的 `run()` 方法。否则会形成“主模型调用一个内部再次调用模型的工具，再总结第二个模型输出”的嵌套链路，增加延迟、成本和信息损失。

当前设计让自然语言生成集中在主 Agent，工具只负责检索或查询。工具边界更容易测试，调用轨迹也能直接展示参数和原始结果。

## 3. 政策检索为什么采用两阶段方案

政策查询同时包含字面关键词、语义需求和地区适用性三类约束：

1. BM25 从本地政策库召回候选，保留专有名词和补贴项目名称的字面优势。
2. 地区硬过滤排除明确不适用的政策，防止高语义相似度掩盖行政区域错误。
3. BGE-small-zh-v1.5 对候选做语义精排，改善用户口语与政策文本措辞不一致的问题。
4. 将向量分、BM25 分和规则分加权，返回 Top-K 和匹配理由。

政策库当前只有 28 条，embedding 矩阵常驻内存即可。引入独立向量数据库会增加部署和维护成本，却不会在这个规模上带来实际收益。本地无结果时才联网检索，并明确标注结果尚未经过本地库核实。

## 4. 诊断路线为什么没有直接上 GraphRAG

病虫害知识库当前有 77 条记录，关系结构简单。主路线使用 RapidFuzz，几乎没有运行成本，也能通过作物过滤保留较强的拒绝能力；对照路线把完整知识库放入长上下文，让模型处理更自由的症状改写。

16 条人工标注用例的真实结果：

| 方法 | 命中率 | 平均耗时 | 主要特点 |
|---|---:|---:|---|
| RapidFuzz | 11/16（69%） | 0.1ms | 快、拒绝稳定，但不擅长插入式改写 |
| 长上下文推理 | 13/16（81%） | 1058.6ms | 改写召回更好，但成本高且更容易误判 |

其中，长上下文在 6 条插字改写用例中命中 5 条，RapidFuzz 命中 1 条；但在 2 条作物不匹配用例中，RapidFuzz 全部正确拒绝，长上下文全部误匹配。因此更合理的后续方向是分层兜底，而不是用生成式判断完全替代规则。

## 5. A2A-lite 为什么只做协议核心

`PlanningAgent` 通过 `a2a_lite.py` 调度三个子 Agent。每个 Agent 提供 Agent Card，每次调用创建统一 Task，并经历 `submitted → working → completed/failed` 状态变化。

这些结构解决了当前项目真正需要的问题：能力声明、统一消息信封、任务生命周期和可观测性。完整 A2A 的服务发现、JSON-RPC 和跨进程传输在当前单进程规模下没有收益，所以被明确留作扩展边界，而不是以“支持 A2A”模糊带过。

## 6. 图片为什么先转文字

项目使用的视觉模型负责观察图片，不负责工具编排。因此图片走确定性预处理：视觉模型只识别作物和可见症状，不给病因结论；识别结果被追加到用户消息，再进入 AgriGraph 的结构化路由和工具链。

这种拆分把“观察”和“诊断”分开，也让现有工具循环无需感知图片格式。视觉调用失败时，系统保留用户文字问题并明确提示改用文字描述，不会假装识别成功。

## 7. 可靠性与验证

- `MyLLM` 只对可恢复的 429 限流执行重试，持续失败时返回清晰错误。
- AgriGraph 的 ReAct 节点设置 5 轮工具调用上限；结构化路由低置信或缺字段时进入 Clarify，不带着不完整参数调用工具。
- 运行代码只保留 AgriGraph；Prompt 与工具注册分别集中到 `agents/prompts.py` 和 `tools/agent_tools.py`，避免主图依赖历史版本。
- `PlanningAgent` 隔离三个并发子任务，单项失败不阻断其他结果和最终汇总。
- 单元测试使用可注入的假 LLM 验证循环、会话隔离、历史恢复、降级和路由；检索测试直接运行 RapidFuzz、BM25 和 BGE 的真实逻辑。
- Streamlit 展示每轮工具名、参数与原始返回，便于解释模型为何得到最终答案。

## 生产化前仍需补齐

- 将 BGE 模型与索引初始化改成显式的启动阶段或惰性加载，并增加就绪检查。
- 为政策数据增加来源、发布日期、有效期和定期更新机制。
- 增加持久化会话、用户隔离、鉴权、限流和敏感信息处理。
- 用更大且分层的数据集评估诊断准确率、拒答率和政策检索 Recall@K / nDCG。
- 收紧 CORS、补充容器化部署和持续集成，并为外部模型与 MCP 服务增加监控。
